Real-Time Web Communication & PWAs

Web Development — Week 8

Polling · HTTP Streaming · SSE · WebSockets · SignalR · WebRTC · Service Workers · Web Push · PWA

Cross-referenced with GPT-5.5 (high). ~3-hour lecture.

1. Why "real-time" matters

  • The web started as a pull medium. Modern users expect push.
  • Chat, AI typing, dashboards, video, multiplayer — all the same question:
  • Who pushes data? When? Over which wire?
  • There is no "best" tech — only the right shape for the problem.

2. Pick the communication model first

  • Direction — S→C, C→S, both, peer↔peer?
  • Latency budget — ms, sec, "eventually"?
  • Fan-out — 1:1, 1:many, many:many?
  • Reliability — must every message arrive in order?
  • Lifecycle — short request, persistent, or background?

Decide the model before you reach for an API.

3. HTTP Baseline

  • Stateless, client-initiated, request → response.
  • Half-duplex per request.
  • Friendly to CDNs, caches, proxies.
  • Every real-time tech either bends, replaces, or bypasses HTTP.

HTTP — when it's still right

  • CRUD, REST, GraphQL queries/mutations.
  • User-initiated reads / form submits.
  • Latency budgets measured in seconds, not milliseconds.

4. HTTP Polling

Short polling: ask every N seconds

Client ──GET /updates──► Server (every 5s)
Client ──GET /updates──► Server

+ Trivial, stateless, universal.

– Wasted requests; latency = poll interval.

4. Long Polling

Client ──GET /updates──► Server (holds…)
                          ↓ data arrives
Client ◄────payload───── Server
Client ──GET /updates──► Server (immediately reconnects)

+ Near real-time, HTTP-friendly, survives proxies.

– Many idle open sockets; one message per round-trip.

Polling — use cases

  • "Is my batch job done?" status checks.
  • Low-frequency dashboards (≥ 30s tick).
  • Hostile-network fallback (still hidden inside SignalR).

5. HTTP Streaming

One long response, body delivered in chunks.

Client ──POST /chat──► Server
        ◄──chunk 1── (token 1)
        ◄──chunk 2── (token 2)
        ◄──chunk 3── (token 3)
        ◄──────────  end

This is how ChatGPT-style "typing" UIs work.

HTTP Streaming — capabilities

+ Client can POST and stream back.

+ Binary-safe, no new protocol.

+ Works with auth headers, middleware, CDN.

– No automatic reconnect (you write it).

– No standard framing — agree on a format (NDJSON, etc.).

– One-way, like SSE.

6. Server-Sent Events (SSE)

Standardized server→client streaming over HTTP. text/event-stream + browser EventSource.

Client ──GET /stream──► Server
       ◄── data: {…}
       ◄── event: update
           data: {…}
       (one persistent response, browser auto-reconnects)

SSE — pros

  • Simplest persistent server→client channel.
  • Built-in reconnection & Last-Event-ID resume.
  • Plays with every HTTP intermediary.
  • Ideal for LLM token streaming, dashboards, feeds.

SSE — cons

  • One-way only. Send back? Make a separate request.
  • Text/UTF-8 only.
  • EventSource cannot send custom headers (no Authorization) — use cookies, short-lived tokens, or fetch-event-source.
  • Long-lived sockets cost memory and file descriptors.

SSE — use cases

  • AI/LLM token streaming.
  • Stock tickers, sensor data, build pipelines.
  • Live sports/election feeds, news, comments.
  • Log tailing in DevOps dashboards.

7. WebSockets

RFC 6455 — upgrade HTTP → persistent, full-duplex TCP channel.

Client                       Server
  ──── GET /ws  Upgrade ────►
  ◄── 101 Switching Protocols ──
  ═══ framed text/binary  ═══►
  ◄═══ framed text/binary  ═══

WebSockets — capabilities

  • True bidirectional, low-latency messaging.
  • Text or binary payloads, optional per-message compression.
  • Subprotocols (graphql-ws, mqtt, custom).
  • Browser-native everywhere.

WebSockets — pros vs cons

Pros

  • Lowest-overhead bidirectional channel.
  • Symmetrical: either side can speak.
  • Predictable latency.
  • Ecosystem in every language.

Cons

  • You own the lifecycle.
  • Sticky sessions + backplane to scale.
  • Proxy hostility — need pings.
  • No HTTP semantics after upgrade.

WebSockets — use cases

  • Chat & collaboration (Slack, Teams, Discord).
  • Real-time collaborative editing (Google Docs, Figma).
  • Multiplayer games & low-latency state sync.
  • Trading dashboards & live auctions.
  • IoT control plane (often via MQTT subprotocol).

8. SignalR

Microsoft's high-level real-time library for ASP.NET Core.

Negotiates transport (WS → SSE → Long Polling) behind a Hub programming model.

SignalR — what you get for free

  • Bidirectional RPC-style method calls.
  • Transparent transport fallback.
  • Groups, users, connection targeting.
  • Automatic reconnection.
  • ASP.NET Core auth integration.
  • Managed scale-out (Azure SignalR Service).

SignalR — pros vs cons

Pros

  • Huge productivity win on .NET.
  • Group targeting without a registry.
  • Built-in fallback + reconnection.
  • Clean cloud upgrade path.

Cons

  • Framework lock-in.
  • JSON default — switch to MessagePack at scale.
  • Silent long-polling fallback hides bugs.
  • Negotiation endpoint is a hotspot.

SignalR — use cases

  • Enterprise chat / collaboration on .NET.
  • Live ops/finance/support dashboards.
  • In-app real-time notifications.
  • Auctions, ticketing, order flow.
  • AI token streaming to .NET clients.
  • Signaling channel for WebRTC (next!).

9. WebRTC

Peer-to-peer, low-latency audio, video, and data — directly between browsers.

Browser A ◄── Signaling Server ──► Browser B
              (SDP, ICE via WS / SignalR)
       │                                  │
       └──── Direct P2P (SRTP/DTLS) ──────┘

WebRTC — pillars

  • MediaStream — mic, camera, screen capture.
  • RTCPeerConnection — codecs, NAT, encryption, transport.
  • RTCDataChannel — arbitrary data (text, JSON, binary).
  • Signaling — your responsibility (WebSockets/SignalR).

WebRTC — infrastructure

  • STUN — discover public IP behind NAT.
  • TURN — relay when peers can't connect (10–25% of sessions). Plan for it.
  • SFU — forward streams beyond ~4–6 peers.
  • MCU — mix/transcode for very large rooms.

"Works on my LAN with just STUN" is a trap. Always test TURN.

WebRTC — pros vs cons

Pros

  • Sub-100ms latency A/V.
  • P2P saves bandwidth + reduces latency.
  • Mandatory encryption.
  • Massive ecosystem.

Cons

  • Substantial complexity.
  • STUN/TURN/SFU infrastructure.
  • Mesh breaks past 4–6 peers.
  • Hard to observe server-side.

WebRTC — use cases

  • Video calling (Meet, Teams, Jitsi, Whereby).
  • Telehealth & telemedicine.
  • Customer support video + screen share.
  • Browser-native multiplayer games (data channels).
  • P2P file transfer & E2E-encrypted chat.
  • Live AI avatars / sub-second agents.

10. Service Workers

A JavaScript file the browser runs in its own background thread — a programmable network proxy between your app and the network.

  • No DOM access — separate global.
  • Lifecycle events: install / activate / fetch / push / sync.
  • Foundation for offline, push, install-to-home-screen.

Service Workers — caching strategies

StrategyBehaviorBest for
Cache-firstTry cache → networkStatic assets
Network-firstTry network → cacheFresh API data
Stale-while-revalidateServe cache, refresh bgAvatars, feeds
Cache-onlyCache, never networkTruly immutable
Network-onlySkip SWAuth, payments

Service Workers — pros & pitfalls

Pros

  • Foundation for offline / push / install.
  • Massive perf wins on repeat visits.
  • Language-agnostic backend.

Pitfalls

  • Cache invalidation is hard.
  • Lifecycle confuses everyone.
  • Buggy SW locks users into old version — keep a "kill switch".
  • HTTPS required (localhost ok in dev).

11. Web Push

Deliver a notification to the user even when the tab is closed. A doorbell, not a data channel.

Server ──VAPID-signed──► Push Service (FCM / Mozilla / Apple)
                                  │
                                  ▼
                       Service Worker `push` event
                                  │
                                  ▼
                       showNotification() → user

Web Push — pros vs cons

Pros

  • Re-engages without an app store.
  • Uses vendor push infra (no pipeline of your own).
  • Strong opt-in / revocable.

Cons

  • Permission friction.
  • iOS needs installed PWA (since 16.4).
  • Not real-time data — best-effort, ~4KB.
  • Easy to abuse → users mute you.

Web Push — use cases

  • Chat / mention notifications while user is away.
  • Calendar / meeting reminders.
  • Order, shipping, ride-share status.
  • Time-sensitive alerts (price drops, breaking news).

12. Progressive Web Apps

A pattern, not a single technology:

  • Web App Manifest — name, icons, theme.
  • Service Worker — proxy, cache, push.
  • HTTPS — non-negotiable.
  • Responsive UI, install prompt, offline, push, background sync.

PWA — pros vs cons

Pros

  • Zero install friction.
  • One codebase, all platforms.
  • Auto updates.
  • Cheap MVP path.

Cons

  • iOS lags on some APIs.
  • Storage quotas can be reclaimed.
  • SW lifecycle is a learning curve.
  • Discoverability outside web.

PWA — examples in the wild

  • Twitter Lite, Pinterest, Starbucks, Uber.
  • News & media (offline-on-the-train).
  • Field-service & logistics in poor connectivity.
  • Internal tools that bypass the store.
  • Note-taking, time-tracking, productivity apps.

13. Adjacent technologies

  • gRPC streaming — service-to-service; browser via gRPC-Web.
  • MQTT — IoT pub/sub; browser via WS bridge.
  • GraphQL subscriptions — live queries over WS/SSE.
  • WebTransport — HTTP/3+QUIC; reliable streams + datagrams.
  • Webhooks — server-to-server "I'll POST you when…".
  • BroadcastChannel / SharedWorker — same-origin tab coordination.

13. Do not use

  • HTTP/2 Server Push — Chrome removed support in 2022. Use HTTP streaming, SSE, or <link rel="preload"> instead.

If AI-generated code reaches for it, replace.

14. Decision tree

  • Anything real-time? No → REST. Stop.
  • Server → client only?
    • Low freq → polling.
    • High freq / stream → SSE (or HTTP streaming for auth POST).
  • Both directions?
    • .NET shop / productivity → SignalR.
    • Else → WebSockets.
  • Audio / video / sub-100ms? → WebRTC + WS/SignalR signaling.
  • Tab closed engagement? → Web Push + Service Worker.
  • Installable + offline? → PWA on top of any of the above.

15. Cross-cutting concerns

  • Scaling — sticky sessions, backplanes, region locality, backpressure.
  • Security — TLS, JWT validated on connect and per call, rate limits, input size caps.
  • Observability — connection counts, p95 latency, reconnect rate, fanout factor, transport mix.
  • Cost — egress dominates; idle connections aren't free; managed services trade $ for time.

16. Recap (one paragraph)

Plain HTTP pulls. Polling fakes push by asking on a loop. HTTP streaming delivers one long response in chunks (today's LLM token UX). SSE standardizes that for server→client with auto-reconnect. WebSockets turn HTTP into a bidirectional pipe. SignalR wraps WS/SSE/long-polling in a productive .NET abstraction. WebRTC opens encrypted P2P media and data between browsers. Service workers are the programmable network proxy that powers offline and background. Web Push rings the user's doorbell when the tab is closed. PWAs package it all into installable, offline-capable apps.
